# Монолит vs микросервисы

📝 Представим себе город, в котором всего одно огромное здание. Все магазины, аптеки и тд находятся в нем- это монолит. И представим себе обычный город, где каждое здание используется для определенной цели- это микросервисы.

📝 Монолит- это большое полотно и все наши запросы идут именно на него. Есть хорошая практика- разбивать это полотно на несколько микросервисов, например, Авторизация, Кешбек, Геопозиция, Поиск.

💡 Большим плюсом такого подхода является то, что разные тестировщики могут тестировать разные микросервисы. При выходе нового билда у монолита необходимо будет проверять абсолютно весь код. При использовании микросервисов у каждого микросервиса будет своя версия билда и тестировать нужно будет только ее.

📝 У монолита один URL, у микросервисов- разные.

## Плюсы монолита

- Простота и легкость разработки
- Единая база кода и общие данные
- Простое развертывание
- В начале их быстрее создавать
- Обычно написан на одном языке программирования

## Минусы монолита

- Масштабирование
- Производительность
- Завязаны на определенном стеке технологий
- Сложное развертывание и обслуживание

## Плюсы микросервисной архитектуры

- Масштабирование и гибкость
- Технологическое разнообразие и самостоятельность
- Отказоустойчивость выше: если один микросервис вышел из строя, то остальные продолжают работать
- Упрощение обновления: можно обновлять каждый микросервис независимо от других
- Легче тестировать: тестируем сам микросервис, а не всю логику, которая есть
- Разные языки программирования: не надо искать программиста на конкретном языке. Обмен информацией реализуем по HTTP

## Минусы микросервисной архитектуры

- Сложная архитектура
- Сложно поддерживать взаимодействия между сервисами и согласованность данных
- Сложно управлять большим количеством микросервисов (это проблема для программистов)
- Сложнее мониторинг: у каждого микросервиса свои логи → нужно помнить, где они лежат
- Поиск ошибки: бывает сложно понять, в каком конкретно микросервисе ошибка. Монолит единый- проблема всегда в нем, но там долго искать ошибку

## Еще один вариант сравнения

Монолит:

- большая кодовая база, в которой смешано много разносторонней логики
- удобно использовать на начальных этапах проекта, но позднее компания распиливает монолит- выделяет из него часть логики в отдельный микросервис
- обычно написан на одном языке программирования
- в начале их быстрее создавать
- один URL

Микросервис:

- небольшая кодовая база, в которой реализована логика по одному направлению

## Что лучше?

Монолит:

- Вся логика собрана в одном месте
- Сломалась какая-то часть (отправка уведомлений) → скорее всего, упадет весь монолит (весь сайт и тп)
- Выходит новая фича- обновляем версию всего монолита и тестируем весь монолит

Микросервисы:

- Вся логика находится в разных микросервисах
- Сломалась какая-то часть (отправка уведомлений) → остальной функционал продолжит работать
- Выходит новая фича- обновляем версию конкретного микросервиса и тестируем только его

## Сравнение по аспектам

| Аспект | Монолитная архитектура | Микросервисная архитектура |
|--------|------------------------|----------------------------|
| Разработка и развертывание | Одна база кода: простые процессы разработки и развертывания | Децентрализованная разработка; каждый сервис разрабатывается и развертывается по отдельности |
| Масштабируемость и производительность | Масштабируемость всего приложения; возможно нерациональное использование ресурсов | Детализированная масштабируемость; оптимальное распределение ресурсов, исходя из потребностей различных сервисов |
| Обслуживание и расширяемость | Единая база кода: проще понять и легче обслуживать | Независимые сервисы; проще добавлять новые функции, не изменяя все приложение |
| Технологическое разнообразие и автономность | Ограниченный стек технологий; привязка к определенному набору технологий | Разнообразие технологий, доступных для каждого сервиса; можно выбрать, какие технологии подойдут лучше |
| Отказоустойчивость | Единая точка отказа. Отказы влияют на все приложение | Изолированные отказы. Отказоустойчивость лучше |
| Координация и взаимодействие | Прямые вызовы функций; более простая коммуникация и обмен данными | Взаимодействие между сервисами; дополнительные средства для координации и согласованности данных |
