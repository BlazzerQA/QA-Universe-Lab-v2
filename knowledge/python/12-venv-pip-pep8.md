# Виртуальные окружения, pip, PEP8

📝 Виртуальное окружение- изолированная “коробка” со своим Python и своими библиотеками. Разные проекты могут иметь разные версии одних и тех же библиотек без конфликтов.

## Зачем venv

- Проект A требует requests 2.28, проект B — 2.31: глобальный Python так не умеет
- Системный Python не засоряется тестовыми библиотеками
- requirements.txt собирается из чистого окружения, без мусора

## Создание и активация

Создать:

    python -m venv venv

Активация Windows (PowerShell):

    venv\Scripts\Activate.ps1

Активация Windows (cmd):

    venv\Scripts\activate.bat

Активация Linux / macOS:

    source venv/bin/activate

После активации в приглашении видно (venv), а pip и python указывают внутрь окружения.

Деактивация:

    deactivate

⚠️ В PowerShell Activate.ps1 может быть заблокирован политикой выполнения: Set-ExecutionPolicy -Scope CurrentUser RemoteSigned.

## pip

📝 pip- пакетный менеджер Python.

    pip install requests           # установить
    pip install requests==2.31.0   # конкретная версия
    pip install -r requirements.txt  # из списка
    pip uninstall requests         # удалить
    pip list                       # что установлено
    pip show requests              # инфо о пакете
    pip freeze > requirements.txt  # дамп текущего окружения

💡 Воркфлоу в автотест-проекте: создал venv → поставил pytest, playwright, requests → pip freeze > requirements.txt → передал коллеге: он создаёт venv и ставит pip install -r.

⚠️ pip freeze дампит всё, включая транзитивные зависимости. “Человеческий” requirements лучше писать руками, фиксируя основные пакеты.

## requirements.txt

    pytest==8.2.0
    requests==2.31.0
    playwright==1.44.0

📝 Список зависимостей проекта с версиями. Даёт воспроизводимость: на любой машине встанут те же версии.

## PEP8 — основы стиля

📝 PEP8- стандарт оформления кода на Python.

- Отступы- 4 пробела, никаких табов
- Длина строки- до 79 символов (в проектах часто разрешают 100-120)
- Именование: переменные и функции- snake_case, классы- CamelCase, константы- UPPER_CASE
- Импорты вверху файла, каждый на своей строке; порядок: стандартная библиотека, сторонние, свои
- Две пустые строки до и после функций и классов верхнего уровня
- Пробелы вокруг операторов: x = 1, а не x=1

💡 Зачем это в команде: код читают в разы чаще, чем пишут. Единый стиль- меньше споров на ревью.

## Линтеры и форматтеры

📝 Линтер находит нарушения стиля и потенциальные ошибки. Форматтер переписывает код по стандарту сам.

- flake8 — линтер PEP8
- black — форматтер “без настроек и споров”
- ruff — современный быстрый линтер + форматтер
- pylint — более строгий анализ

Установка и запуск:

    pip install ruff
    ruff check .     # найти нарушения
    ruff format .    # отформатировать

💡 В CI нормальных проектов ruff/black гоняются на каждый pull request: стиль не прошёл- мерж запрещён.
